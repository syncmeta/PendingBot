# Session 健康感知

> session 的进程「活着」不等于 agent「能干活」——claude 没登录、额度到顶、codex token 失效时,进程照常跑着,活却一步都动不了。本篇讲 PendingCrew 怎么**不靠人进终端肉眼看**就感知这类故障,并把它 fail-loud 地浮出到成员状态点、成员列表和群聊白板。相关:[Runner 后端](runner-backends.md) · [三栏布局](three-pane-ui.md) · [白板](../concepts/whiteboard.md) · [本机子进程安全](subprocess-safety.md)。

## 逻辑

**健康异常 = 进程存活但 agent 干不了活的状态**,独立于「running / exited」生命周期。v1 覆盖两类:

1. **未登录 / 登录失效**(authRequired)——claude 未登录、key 无效;codex ChatGPT token 失效。
2. **额度受限**(usageLimit)——usage limit 到顶、余额不足。

**检测面按 runner 分两条路,只用可靠信号、不猜:**

- **claude(PTY 终端)**:对终端输出做**去 ANSI 的文案匹配**。匹配短语从本机安装的 claude CLI 二进制实测核出(不是凭印象写的),每类故障只报一次(TUI 反复重绘不刷屏)。
- **codex(app-server)**:协议级信号——codex 发 `account/*` server-request(要客户端刷新 ChatGPT token)而客户端无法提供时,即登录态失效。仍旧回错误应答让 turn 不挂死,但**同时翻健康位**,不再当 unsupported 静默丢。

**浮出三处,一次故障三种视距都看得到:**

1. **成员状态点转红**——头像右下角状态点加「异常」档(红),与 干活中(绿)/空闲(黄)/退出(灰)并列;进程还活着但干不了活,一眼区别于正常状态。
2. **成员列表副行显示故障详情**——健康异常优先于「最新动作」,内容是人话 + 下一步动作(「跑 /login 登录」「等额度窗口重置」),不是错误码。
3. **群聊白板 fail-loud 一条**——以该 session 名义往本 crew 白板发「⚠️ 出问题了：…」,category=error;人不盯成员列表也会在群聊里撞见,captain / 其它 session 下轮注入白板时同样知道这个队友挂了。

## 为什么

- **「没消息」和「没问题」必须可区分。** 之前 claude 没登录时 crew 完全不报错——用户看到的只是 session 一直安静,以为在干活,实际一个字都没跑。健康感知把「安静 = 空闲」和「安静 = 挂了」拆开,是多 session 协作里最基本的可观测性。
- **fail-loud 到群聊,是因为白板是 crew 的共识层。** 只亮状态点的话,只有正盯着成员列表的人知道;发进白板,人、captain、其它 session(每轮注入)都自然获知——「队友挂了」本来就是关键节点,该走 [白板](../concepts/whiteboard.md) 的关键节点语义。
- **每类故障只报一次,是白板不被淹没的底线。** claude TUI 对同一错误会反复重绘;不去重的话一条「没登录」能刷出几十条白板消息,fail-loud 变噪音。
- **只用实测信号,是被「凭印象写字段」的教训逼出来的。** claude 的匹配短语全部从本机 CLI 二进制 strings 里核出;codex 只用协议里真实存在的 `account/*` 请求。不可靠的信号(如「网络故障 vs 登录失败」的自动区分)宁可不做,留给人看 detail 判断。

## 用在哪 · 长什么样

- **成员列表 / roster 头像**:状态点红 = 健康异常;点开该 session 的行,副行直接是故障说明与修复动作。
- **群聊中栏**:一条来自该 session 的「⚠️ <名字> 出问题了：<详情>」消息,和普通进展消息同渲染。
- **修复动作是人工的**:登录 / 充值这类操作必须人来做(agent 自己做不了),所以详情文案永远带「怎么修」——打开该 session 终端跑 `/login`、`codex login`、等额度窗口重置。

## 示例

你在 crew 里派了个 claude worker 跑重构,中途 claude 订阅额度到顶。终端里滚过一行「You've reached your usage limit…」——PTY 扫描命中,worker 的状态点转红,成员列表副行显示「额度受限——等额度窗口重置或检查订阅后再继续」,群聊里出现一条「⚠️ Claude Code · a1b2c3 出问题了：…」。你在群聊里就看到了,不用逐个点开终端排查为什么活停了。

## 边界

- **本篇只管「感知 + 浮出」,不管自动修复**——不自动重登录、不自动重试、不自动停 session;修复动作(登录/充值)本来就需要人。
- **v1 只覆盖 未登录 / 额度受限 两类**;进程 crash 的 exit code 已有生命周期状态管;更细的运行时错误分类(网络故障、模型报错)不在本篇。
- **额度的「事后感知」不是「事前预算」**——用量监控/预警(接近上限提前变色)是相邻主题,不在 v1。
- **文案匹配只服务 claude 的 PTY 路径**;codex 走协议信号,不扫 transcript 文本。

## 注意

- ⚠️ **PTY 文案匹配对 claude CLI 版本敏感。** 短语表锚定实测版本;claude 改版文案可能漏检(检不到 ≠ 健康)。升级 claude 后若健康感知失灵,先对新二进制重新 strings 核短语表。
- ⚠️ **内容级误报是已知取舍**:终端里**内容**出现匹配短语(比如 agent 正在 cat 一份含 "run /login" 的文档)会误报。它是提示性 warning、每类只一次,接受这个噪音换取零漏检成本;别为消灭误报把短语表收窄到漏掉真故障。
- **状态点的红有两个含义**(未读红点 / 健康异常),未读优先级更高——有未读时健康红被盖住,详情仍在成员列表副行与白板消息里。
