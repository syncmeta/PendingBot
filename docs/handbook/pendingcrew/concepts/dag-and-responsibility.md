# Crew DAG 与责任比例

> [Crew](crew.md) 之间能结成父子关系,组成一张有向无环图(DAG);每个 crew 的花销按比例算到它的责任主体上。这套规则的产品意图只有一个:**保证每个 crew 永远有一个明确的"拍板方"**。相关:[crew](crew.md) · [captain](captain.md) · [群账号权限](../../shared/concepts/group-permissions.md)。

**逻辑**

- **DAG 结构** —— crew 之间是**多父多子**的有向无环图。类比:公司里一个小组可以隶属多个部门。环是被禁止的——认一条会形成环的父子边会被拒。
- **父子消息路由**(权限来自 DAG 边,不来自消息同步):
  - **父 → 子**:父说的话**留在父 crew 的白板**,不自动灌进子 crew;子 crew 的 captain 自己读、自己判断要不要拆解给子组。
  - **子 → 父**:由子 crew 的 captain 在父 crew 群聊里发**摘要**(不发完整聊天记录、不发完整 session 日志)。
  - 父成员 / 人类可以**直接进子 crew** 跟成员说话,这个权限来自 DAG 边。
- **责任比例** —— 一个 crew 的总责任永远是 100%,按比例分给它的责任主体(可能是个人 user 或群 group)。五条规则:
  1. **认父时定死,不是事后协商** —— crew C 当前由某主体 100% 控制;当它被认作另一个 crew 的父(让对方参与 C 的责任分配)时,**就在认父这一刻**决定保留多少比例(保留 >50% → 原主体仍是拍板方;<50% → 对方拍板)。之后要改,必须明确发起一次"修改责任比例"动作,不能含糊地"协商重分配"。
  2. **不允许相同 / 不允许平均** —— 同一个 crew 里任意两个主体的比例**不允许相等**。bot 协商比例时只能在"非均等合法解空间"里挑。
  3. **同主体合并** —— 多父时,同一个主体从不同父带来的份额相加,再归一化到 100%(例:X 从父 A 带 40、从父 B 带 70 → 合并 110,与其他主体一起归一化)。
  4. **跨主体确认** —— 多父的责任主体集合**不同**时,**各方人类必须批准**;集合**相同**时,bot 自己协商无需人类。
  5. **拍板原则** —— 每个 crew 永远有一个"占多数"的责任主体(**拍板方**)。当 captain 之间出现指令冲突、或模型在多父消息里幻觉跟错指令时,**听拍板方的**。
- **环检测是双保险** —— **数据库层 + 服务层都拦**:DB 侧用递归 CTE 触发器拒绝成环的边,edge 侧再判一道(会形成环时返回 `crew_cycle` 409)。
- **跨主体确认走权限矩阵** —— "人类批准"在群账号场景下 = 走**群权限矩阵**(admin+ 批,不要求全员);个人账号场景下 = 本人批准。

**为什么**

- **规则 2(不允许相同)的产品意图是"永远有拍板方"** —— 如果两个主体能各占 50%,captain 之间一旦扯皮、或模型在多父消息里跟错指令,就没有一个明确的"听谁的"。强制非均等,保证每个 crew 都有一个占多数的责任主体来一锤定音。规则 5 把这条落到 bot 系统提示里强调。
- **跨主体要人类确认,是因为它等于"把成本摊给别人"** —— 把自己的 crew 认作别人的子(请别的主体来"领养"),会让对方的钱包参与分账;这种跨主体的责任变更必须各方人类点头,不能 bot 自己拍。同主体内部的份额调整无此风险,放给 bot 协商。
- **"等对方批准"是产品本意的同步语义,不是 bug** —— 对方人类不在线就等。crew 协作里"异步等批准"是刻意的设计。

**用在哪·长什么样**

- **新建子 crew**:在 crew 详情里有「新建子 crew」入口,自动把当前 crew 挂为父;认父时按规则 1 定份额。
- **修改责任比例**:发起一次份额变更提议,系统算出"必须批准的主体集合"(提议里出现的主体 ∪ 当前持份的主体——这样被移除的主体也有一票),各方人类逐一批准后才生效。
- **侧栏 / 详情**:crew 之间的父子边渲染成 DAG 树;责任份额在详情里展示。

**示例** — 你 100% 拥有 crew C。你想让团队的"支付组"crew D 参与 C 的工作,于是把 C 认作 D 的子。认父这一刻你决定 C 自己保留 40%、D 占 60%——于是 D 是拍板方。因为 C 和 D 的责任主体不同(你 vs 支付组那个群),这次变更要**对方人类批准**:走支付组的群权限矩阵,admin 点头即可,不用全组到齐。批准前请求挂起等待——这是同步语义,不是卡死。

**边界**

- 多父多子,但**禁止成环**。
- **总责任恒 100%**;任意两主体份额不相等。
- 父子之间**不自动同步消息**:子→父只发摘要,父→子靠子 captain 主动读。
- 跨主体的责任变更要人类批准;同主体内部份额由 bot 协商。

**注意 — 易错点**

- ⚠️ **这套 DAG / 责任分账目前是 edge(Supabase RPC)实现的**,而 PendingCrew 的大方向是「本地为家、edge 是邮差」。审计(`docs/stale-model-audit-2026-06-15.md`)曾把"crew 组织 / DAG 还建在 edge 上"记为一条 🔴 结构债——DAG 与分账这部分**尚未跟 captain 编排一起搬回本地**。本篇描述的是**当前 edge 上确实在跑、且经单测验证**的行为;它在 local-first 收口里的最终落点待定。
- ⚠️ **`spawned_by_captain`(父 captain 创建子 crew、子 captain 默认继承父 captain)是 legacy 路径** —— 它由 `/v1/crew`(单数)路由的 `create_child_crew_inheriting_responsibility` RPC 承载,**不是**当前建 crew 的主路径(主路径是 `POST /v1/crews` 复数,captain 来源只 `system_generated`)。老 `decisions.md` D4 把它当"第 4 种 captain 来源"补进 spec,这条**已部分过时**:认父继承的责任链路还在,但"captain 来源 4 种"的说法在当前主路径上不成立(见 [captain](captain.md) 篇)。
- ⚠️ **群账号场景的"人类批准"= 群权限矩阵,不是全员** —— 别误以为跨主体要全组同意。admin+ 批即可,这是为了避免"旅游群有人手机没电卡住所有人"。群权限矩阵本身的后端有了、客户端尚未完全消费(见群权限篇)。
