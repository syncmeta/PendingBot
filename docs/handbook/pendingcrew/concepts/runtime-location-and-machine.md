# 运行位置与 Machine(机器)

> 一个 crew 里的 coding agent 实际跑在**哪台机器**上,是 PendingCrew 的一等概念。本篇讲这个抽象:本机 / peer / fly 三种位置统一收进**一张机器清单**,本机只是其中一台;以及为什么 peer 和 fly 在架构上是同一种东西。相关:[Crew 与 Captain](crew.md) · [本地为家](local-first.md) · [跨设备控制](../features/cross-device-control.md)。

## 逻辑

**Machine = 一台「有能力真正跑 coding agent 的机器」。** 一台 Mac、一台 iPad 能遥控的已登录电脑、一台云端 box——在产品心智里都是「机器」,统一进同一份**机器清单**(账号级,RLS 只看得到自己账号的机器)。每个 crew 引用其中一台机器,表示「这个 crew 的 agent 跑在那上面」。

三种机器,派生自同一份清单(不是三个并列的死枚举):

| | 本机(local) | peer(对等电脑) | fly(云机器) |
|---|---|---|---|
| 是什么 | PendingCrew 当前所在的这台机器 | 同账号下另一台已登录的电脑(主要给 iPad 遥控用) | 云端 box |
| 怎么识别 | 机器清单里 `device_id` == 当前设备标识的那台 | 清单里其它电脑类机器 | 清单里 fly 类机器 |
| 谁跑 agent | 这台机器本身 | 那台对等电脑(本机只是控制面) | 云 box(本机只是控制面) |
| 算力计费 | 免费(用户自己的设备) | 免费(用户自己的设备) | 按时长扣责任主体钱包 |

**「本机」不是特殊位置,只是清单里 `device_id` 匹配当前设备的那一行。** 登录后,每台电脑把自己 upsert 进清单(写显示名 + 最近在线时间)。这样「我自己」和「我账号下的另一台电脑」用的是同一套数据,不需要为「本机」单开一条码路。

## 为什么

- **把「运行位置」做成一等的 machine,而不是三档枚举,是为了让 peer / fly「天然在册」。** 早期把位置建模成 crew 上的一个 `runtime_location` 枚举(`local_host` / `peer_device` / `fly_machine`)+ 两个外键列(peer 一个、fly 一个),既繁琐又把「机器」这个实体藏了起来——iPad 要遥控哪台电脑、有没有在线,无处可挂。升成 machine 表后:一份清单同时回答「我有哪些机器、各自在不在线、这个 crew 在哪台上跑」,iPad 遥控、fly 选择、本机识别全落在同一个抽象上。
- **关键洞察:peer 和 fly 是同一种东西——「一台有进程能力的远程机器,本机只是控制面」。** 两者复用同一套通信架构:身份(账号同步)、指令转发、状态同步、审批通道、白板注入。唯一区别是计费(peer 免费 / fly 按时长)和机器生命周期(peer 是用户自己开关电脑 / fly 是用户在 app 里开关 box)。这条洞察决定了实现顺序:**把 peer 做通,fly 的通信层就已经铺好了**,fly 剩下的只是云 API 集成 + 按秒计费 + box 管理 UI。这也是 v1 → v1.1 过渡格外自然的根本原因。
- **机器清单只挂本人账号、RLS 锁死。** 一台机器属于一个人;遥控只发生在同一账号的多台设备之间,别人既看不到也碰不到。

## 用在哪 · 长什么样

- **侧栏按机器分组**:PendingCrew 侧栏不是平铺的 crew 树,而是**每台机器一组**,crew 住在它所属机器组下。顺序:本机置顶 → 其它电脑(peer)→ fly → 解析不到的落「其它」桶。本机组带「+ 新建」入口,其它机器组(暂时)只能遥控查看。
- **新建 crew 选机器**:只有「已登录且机器数 > 1」时,新建表单才出现机器选择(平铺药丸按钮);否则不显示,crew 默认挂本机。未登录时根本没有机器清单——永远只有本机一台。
- **在线点**:每台机器组头有个在线状态点(给 iPad 判断「这台电脑现在能不能遥控」)。

## 示例

用户在 Mac 上登录 PendingCrew,Mac 把自己 upsert 进机器清单(显示名「我的 MacBook」)。之后他拿 iPad 打开 PendingCrew,iPad 也登录同一账号——iPad 的侧栏里能看到「我的 MacBook」这台机器(在线点亮着),iPad 自己不跑本地 agent,但可以把任务派到这台 Mac 上(peer 遥控,见现状尾巴)。如果他之后开了一台 fly box,清单里再多一台云机器,新建 crew 时就能在「本机 / 我的 MacBook / 那台 fly」之间选。

## 边界

- **本篇只讲「crew 跑在哪台机器」**。crew 的工作目录(crew 默认 cwd、session 可覆盖、CrewGround 随机目录)是相邻但不同的主题,见 [create-crew-and-session](../features/create-crew-and-session.md)。
- **机器清单只在登录态存在**。未登录 PendingCrew(纯本地)永远只有「本机」一台、不显示机器选择、crew 不挂任何机器——见 [本地为家](local-first.md)。
- 跨账号遥控不存在:只能控自己账号下的机器。

## 注意 — 已改的旧建模(别写回)

- ❌ **`runtime_location` 三档枚举 + `peer_device_id` / `fly_machine_id` 两个外键列** —— 已收口成 crew 上单个 `machine_id`。「本机/peer/fly」现在是**从机器清单派生**(看 `device_id` 匹配 / 机器类型),不是存在 crew 上的死枚举。`runtime_location` 即便还作为派生镜像列存在,也只是历史兼容、`machine_id` 才是事实源,日后可清。
- ❌ **「peer 和 fly 是两套不同机制」** —— 它们是同一种东西(同一套远程通信架构),只在计费和生命周期上不同。任何把它们当成两条独立链路来设计的说法都已作废。
- ⚠️ **edge 侧的 `session-world-model.ts` 渲染器和世界观 prompt 里仍能看到 `runtime_location` 字样**——那是 `.logged` 边路的历史残留,不代表当前本地建模;本地侧已是 machine 模型。引用时以本篇为准。
