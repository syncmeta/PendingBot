# Voice Container(群语音媒体引擎)

群语音的实时音频引擎,跑在 Cloudflare Container(CF 容器里的 Bun 进程)。相关:[Durable Objects](durable-objects.md)(RoomVoiceDO 控制面)· [群语音 feature](../../pendingbot/features/voice.md)。

> 这块经历过两次架构换代,务必按现状(v3)理解(见文末「注意」)。

**逻辑**
- **它是什么** — 一个真正的 OS 进程(Bun),每个进行中的群语音房间一个实例。它是房间里所有人和 bot 的**音频汇聚点**:人和 bot 都是 Cloudflare RealtimeKit 的 WebRTC 参与者;容器把每个 bot 听到的音频(其他人 + 其他 bot)桥接给模型语音端,再把模型生成的语音按稳定节拍播回房间,同时喂给其他 bot 的"耳朵"。
- **职责切分** — **音频 + 节奏全在容器**,**策略全在 DO**:权限、计费、在场 / 名单这些控制面留在 RoomVoiceDO,容器只管媒体。两者通过一条控制 WebSocket 连起来。
- **抗断续是核心** — 容器里用稳定时钟(Bun 的 `setInterval`)按固定步长输出音频,加一个预滚缓冲吸收模型那边突发的数据块。"稳定时钟 + 缓冲"这对组合,就是不卡顿的核心。
- **只在内网可达** — 容器的所有端点(健康检查 / 控制 socket / headless bot 参与页 / bot 音频桥)都只通过 Worker 到达,不暴露公网;凭每房间的令牌核身。

**为什么**
- **workerd 跑不动实时音频** — Worker 的 isolate 在事件间会被调度走、定时器会漂移,表现成 bot 语音断断续续。实时音频需要一个有可靠定时器和线程的真进程,所以把音频循环从 isolate 搬进容器。
- **DO 只留控制面** — 把"会变、要强一致、但不吃 CPU"的策略留在 DO(便宜、近免费),把"吃稳定 CPU"的媒体搬进容器(按需起、用完回收),各司其职。
- **实例规格按需** — 容器用的是"够稳"的小档而非最小档:最小档那点 CPU 切片会重新引入当初要消灭的卡顿;并发上限按"发布前够用"设,流量起来再抬。

**用在哪·长什么样**
- 用户感知不到容器;它表现为群语音里"多个 bot 能同时在场、轮流说话、声音不卡"。
- 一通群语音开始时按需拉起一个容器实例,结束(DO 发"结束"信号 + socket 关闭)后及时回收闲置实例,不为"热但空"的容器付费。

**边界**
- 容器**不做策略**:权限 / 计费 / 名单不在这里,在 RoomVoiceDO。
- 是**群**语音的引擎;1:1 语音走的是另一条路径(模型实时端 + WebRTC,不进这个容器)。
- 不暴露公网,不是一个可独立访问的服务。

**注意 — 已死的旧方案(别写回)**
- ❌ **v2:在 Durable Object 里做混音** —— 已废。isolate 定时器漂移导致卡顿,这正是搬进容器要解决的问题。
- ❌ **把实时音频留在 workerd isolate** —— 同上,已搬走。
- 现状是 **v3**:音频在 CF 容器里抗断续,DO 只留控制面。

**现状** — 🟨 群语音整套(RealtimeKit + 容器媒体引擎 + RoomVoiceDO + 计费)代码已落、已合 main,含单测。端到端真机 / 多人多 bot 的实景 QA 仍属待验范畴;且现网计费总开关默认关(不影响通话本身)。
