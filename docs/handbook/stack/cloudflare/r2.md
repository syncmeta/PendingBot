# R2(附件 / 头像对象存储)

Cloudflare R2 = S3 兼容的对象存储(出口免费)。大绿豆用它存附件和头像的字节。相关:[Edge](edge.md) · [附件 / 信封 feature](../../pendingbot/features/envelope-inbox.md) · [头像可见性概念](../../shared/concepts/avatar-visibility.md)。

**逻辑**
- **它是什么** — 存"大字节"的地方:用户上传的图片 / PDF / 文件、头像。数据库里只存指针(对象键 + 元数据),字节本身在 R2。
- **内容寻址 + 跨用户去重** — 上传的对象按内容哈希命名(`blobs/<sha256>.<ext>`)。两个人传同一份字节,只在 R2 落一份对象;每个人各自有一条**自己的附件行**(带自己的会话归属 / 配额计数),共享底层对象但互不可见对方的元数据。
- **id 即能力(id-as-capability)** — 取字节走 Edge 的 `/v1/uploads/:id`:拿着这个**不可枚举的附件 id** + 通过鉴权,就能取到字节;服务端每次请求**重新核成员资格**,不靠 R2 自己发公网 URL。R2 对象不直接对外暴露。
- **额度 + 单文件上限** — 单文件有上限(当前 25 MB,对所有类型一视同仁),每用户有云端总配额(当前 1 GiB,可由 board 配置覆盖,缺省走代码兜底)。

**为什么**
- **出口免费 + 零 VPS** — 党纲商业立场:关键基础设施外包、零 VPS;R2 出口不计费,贴合"附件这种重出口"的成本结构。
- **内容寻址省存储** — 同一张图被多人转发 / 多处引用时只存一份;去重在上传时按哈希做。
- **能力式取字节而非公开 URL** — 大绿豆是隐私敏感的聊天产品,默认收紧:附件不该有"知道 URL 就能拿"的公开链接,而要每次经 Edge 重新鉴权 + 核成员。把"id 不可枚举 + 服务端核权"绑在一起,胜过签名 URL 那种"签发后失控"的模型。

**用在哪·长什么样**
- 用户在聊天 / crew 白板里发图片 / 文件、设头像 → 字节进 R2,消息 / 资料里挂的是附件 id。
- 看图时客户端拿 id 向 `/v1/uploads/:id` 请求(带鉴权)→ Edge 核权后回字节。用户只看到"图能加载",看不到 R2。

**边界**
- R2 **只存字节**:归属 / 配额 / 会话关联这些元数据在 Postgres 的附件行里,不靠 R2 对象的 customMetadata 当事实源。
- 不发公开直链;取字节一律经 Edge 鉴权(id-as-capability)。
- 不是数据库,不做查询;按键(内容哈希)存取。

**注意**
- **共享对象 + 私有行**:多人传同字节 → 共享一个 R2 对象,但各自的附件行(会话归属 / 配额)互不可见。对象上残留的"首个上传者"元数据**不对外surface**——取字节走的是各用户自己的行。
- **额度兜底要对齐**:每用户配额的代码兜底值必须和 billing_config 的 seed 一致,免得"配置被清空"时静默放开配额闸。

**现状** — ✅ 附件上传 / 取字节(内容寻址 + 跨用户去重 + id-as-capability + 配额)已落地并在生产用。crew 白板附件(发送 + 渲染)也已接上同一套 R2 路径。
