# 手册写作规约

## 高度

站在**产品经理 / 决策者**的高度:给产品逻辑、思路、取舍。精度上限 = **"照着走,产品策略不跑偏"**,到此为止——**不下到实现**(实现交给代码 + stage docs)。

不写形式化需求(不用 EARS 那种 `WHEN…SHALL…`),不套完整 SDD。这些只是借来理清结构,不是来上规矩的。

## 粒度(一主题一文件)

一个**可独立查找的主题** = 一篇文件,保持下面的厚度。别在一篇里塞多个并列主题——开发时要能照目录索引直接定位到需要的那篇。一篇里若出现多个并列的大主题(像"加好友 / bot 邀请 / 群邀请"),拆成各自的文件;每篇仍按下面的模板写满。

## 每篇的松散模板

每篇是**纯意图、不带状态**(状态记在现状 handbook `docs/state/`,见下),正文按下面的**默认结构,不是死表**——哪节这篇用不上就省,够清楚就行:

```
# <中文标题>

**逻辑** — 它是什么、怎么运作(产品视角)
**为什么** — 背景 / 取舍
**用在哪·长什么样** — 出现在产品哪个位置、用户看到 / 做什么
**示例** — 一个具体场景走一遍
**边界** — 明确不做什么
**注意** — 坑 / 要小心的问题
```

- `concepts/` 里每篇**写成产品决策的形状**(逻辑 + 为什么 + 边界),它就是这条概念的权威定义。旧 `docs/decisions.md` 的 D1–D5 升华并入对应概念。
- `features/` 里每篇是这个功能的产品说明(逻辑 + 用在哪长什么样 + 示例)。
- `stack/` 里每篇只到"它是什么、在系统里什么角色",不写配置 / 集成细节。

## 现状记在哪 —— 现状 handbook(`docs/state/`)

手册本身**只写期望、不带状态**。状态、证据、task 链接都落在**另一棵镜像树** `docs/state/`(详见 [声明式对账](pendingcrew/concepts/reconciliation.md)):

- **镜像结构** —— `docs/state/<区>.md` 与 `docs/handbook/<区>/` 路径一一对应;对齐 = 同路径并排看期望 vs 现状。
- **一条 = 一个概念/功能**,标题键 = handbook 相对路径(如 `## concepts/crew`),字段:

  | 字段 | 含义 |
  |---|---|
  | `status` | `planned` / `partial` / `done`(可加 `pending-qa`);判"做没做"以此为准,别把"代码写了"当 `done` |
  | `现状` | 一句话:实际是什么、和意图差在哪 |
  | `证据` | commit / 测试 / 真机 / 部署 指针;没有写 — |
  | `task` | 相关 task id(双向:现状条→task,task 描述也反链回 handbook 概念) |

- **每 session 强制刷** —— 改完代码顺手刷对应现状条(= Terraform `refresh`),不刷则对账失明。

**为什么挪出正文:** 状态属现状层,不混进表达意图的期望页(先做减法,正文只剩产品逻辑);结构化字段能被未来驾驶舱直接渲染,emoji 散在正文里解析不了。

> **存量待迁:** 现有期望页正文里的 ✅🟨⬜「现状」段(及个别页的 frontmatter `status`)迁进 `docs/state/` 是一件机械 sweep 活,单独做。

## 权威层

手册是权威层:与 `docs/superpowers/specs|plans/` 等 stage docs 冲突,**以手册为准**。需要细节出处时,给一个向下的指针(链到 stage doc),不在手册里重抄实现。

## 配套账本

- `docs/tech-debt/` — 一债一文件 + frontmatter(结构化,可被未来 PendingCrew 项目驾驶舱渲染)。
- `docs/progress.md` — 编年 rollup,单文件不动。
- 账本现在是**仓库级一份**;"一 crew 一份"是未来 PendingCrew feature 的事(task #439),格式先对齐、不急着切。
