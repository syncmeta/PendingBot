# 群邀请码

群邀请走和 [bot 邀请](bot-invites.md) **同一套**"邀请关联到人"的哲学,但形态是**每人一码**。核心权威 = 决策 D2。相关:[加好友](add-friend.md)。

**逻辑**
- 每个群成员看到的是**关联到自己的那份**群邀请码。
- 用起来仍是"群的码"——别人扫了就进**这个群**;但每个人签发的码不同,从而留痕**谁是被谁拉进来的**(`invited_by` 落到成员行)。
- 任何群成员都能签发自己的群邀请链接 / 二维码,默认有有效期、可撤销。

**为什么** — 老方案群 handle 是**单一共享码**:谁拿到都能请求加入,**不记是谁分享的**,和 bot 邀请哲学不一致。D2 把群也统一成"邀请关联到人",让 bot 和群共享同一套留痕模型。

**用在哪·长什么样**
- 任一成员在群里出示自己的二维码 / 链接(每人各自一份)。
- 受邀者扫码 → universal link `/g/<token>` → 预览群信息(标题、成员数)+「由 X 邀请」→ 加入。
- 加入按群的**加入策略**走:开放扫码即进的直接进;需审批的则**落一条加入申请**(同样带 `invited_by`),由群里有权的人同意。

**示例** — 群里小李把自己的群二维码发给你。你扫 → 看到"周末爬山群 · 12 人" +「由小李邀请」→ 加入。你这条成员记录上 `invited_by=小李`。隔壁老王从群主那拿的是另一张码,他进来记的就是 `invited_by=群主`——同一个群,各自的码,各自的来路。

**边界**
- 签发要求是**群成员**(非成员不能签发该群的码)。
- 撤销:链接签发者或群主 / 管理员可撤销。
- 旧的 `group_join_handles` 单一共享码已不作主分享路径(后续可清)。

**注意**
- 群邀请预览端点也走**限流**(同 handle 查找桶),挡枚举。
- 加入是"进群"还是"递申请",取决于群本身的加入策略,不取决于邀请码本身。
