# 语音通话

PendingBot 的实时语音:**1:1 跟一个 bot 打电话**,以及**群语音(多人 + 多 bot 同处一个房间)**。两者都是真·实时音频(OpenAI Realtime),但拓扑和承载不同——1:1 是一条直连/代理的双人链路,群语音是 SFU 多方混音。相关:[群分摊](../../shared/concepts/group-pledge.md) · [群权限](../../shared/concepts/group-permissions.md)。

## 1:1 语音

**逻辑**

- 用户和**一个 bot** 打实时语音电话。bot 的「嘴」是 OpenAI Realtime,语音 / 断句风格按 bot 配置。
- **两条传输,按场景择一**:
  - **sideband(WebRTC)** —— 音频是 iOS ↔ OpenAI 的直连 WebRTC(移动端延迟最好)。服务端不在音频路径上,但会另开一条**只读控制连接**到同一通话,拿到同样的用量事件来计费。
  - **proxy(WebSocket)** —— 音频以 WebSocket 帧经服务端中转(iOS → Cloudflare → OpenAI)。服务端在路径上,直接计量;且因为这一跳由 Cloudflare 出口,**在直连 OpenAI 被地区封锁的地方也能用**。
- **计费防作弊**:用量一律从 OpenAI 权威的「回合完成」事件**服务端读取**,客户端无法少报来逃费。余额耗尽或撞到 30 分钟硬上限时,服务端可直接挂断。

**为什么** — 设备永远拿不到供应商 / Cloudflare 凭证(都在服务端),既防凭证泄露、又让计费不可篡改。两条传输并存是为了「既要最佳延迟、又要在受限网络可用」——能直连就直连,直连不通就走代理。

**边界** — 单通话硬上限 30 分钟;凭证从不下发到设备。

## 群语音(SFU)

**逻辑**

- **一个群、一个房间、多人 + 多 bot 同时在场**。真人和 bot 都是 Cloudflare RealtimeKit 的 WebRTC 参与者(SFU 拓扑);每个 bot 各有自己的 OpenAI Realtime 连接,能听见房里其他人 + 其他 bot 的声音、也对所有人说话。
- **控制面与媒体面分家**(这是当前 v3 架构的核心):
  - **控制面 = Durable Object(RoomVoiceDO)** —— 一个通话一个实例。管生命周期、在场名单、角色 / 权限、邀请、广播、计费。**不碰音频字节**。
  - **媒体面 = 媒体容器(voice-container,Bun 进程)** —— 跑每个 bot 的无头 WebRTC 客户端、OpenAI Realtime 连接、音频混音和**稳定的播放时钟**。
- **为什么音频在容器、不在 DO**:实时音频需要一个有可靠定时器和线程的真 OS 进程。Worker isolate 在事件之间会被挂起、定时器会漂移,表现为 bot 声音断断续续。容器里 Bun 的稳定 20ms 输出时钟 + 预缓冲垫,是「抗断续」的核心。
- **房间角色与不变量**:
  - 发起人、群主 / 群管理员**全程**有特权(call-admin)。
  - call-admin(人**或** bot)能踢人、结束通话、指派他人为 call-admin。
  - **铁律:房间永远要有一个真人 admin**。踢掉 / 移除最后一个真人 admin 被拒;最后一个真人离开时通话结束。bot 全走了不结束(只要还有人),人全走了才结束。
- **bot 也有「手」**:每个 bot 都有挂断自己(leave_call)的工具;被指派为 call-admin 的 bot 额外获得结束通话 / 踢人 / 指派 admin 的工具——和真人 admin 同权,但上面那条真人 admin 铁律仍然成立。
- **抗断容灾**:DO ↔ 容器的控制链路有心跳;断了不立刻结束通话,而是进入有界的重连 + 状态重放(在新容器会话里重建房间),只有在时间预算内每次重连都失败才真正收场。

**为什么** — 群语音要同时容纳多个会说话的 bot,延迟和稳定性比 1:1 更难。把「媒体」放进能跑稳定时钟的容器、把「控制 / 权限 / 计费」留在 DO,各司其职:DO 状态可持久 + 可恢复,容器专心抗断续。

**用在哪·长什么样**

- 群会话里发起语音通话 → 房间起来,成员陆续加入,可邀请其他人 / bot 进来。
- 通话中能看到在场名单 + 待接受的邀请 + 诊断信息(实时广播到会话频道)。
- 成本实时预览广播给在场成员;计费按群的分摊模型走(见下「计费」)。

**计费**

- 每个 bot 的语音回合 token 走统一的审计 / 计费路径;RealtimeKit 的媒体参与分钟(按真人 + bot 在场时长)在通话结束时一次性结算。
- 群通话的花费按**群分摊**结算:落到群的「责任主体」钱包(实缴池衰减 + 认缴成员个人钱包分扣);1:1 或无责任主体时落发起 / 计费用户的个人钱包。供应商 USD 直接换成内部计价单位、**无平台加价**。

**边界** — 单通话同样 30 分钟硬上限。Mac 端语音是「硬件 / 平台真没有的」一类,可能不随三端共享(见 [三端 UI](tri-platform-ui.md));语音属 iOS-only 留存项。

**注意 — 已死的旧架构(别写回)**

- ❌ **群语音 v2 的「DO 内混音」** —— 已废。早期把实时音频混音放在 Durable Object 里,workerd isolate 定时器漂移导致 bot 音频断续。**v3 把媒体整体移进容器,DO 只剩控制面**,零混音残留(这是 stale-model 审计里「最干净」的两个维度之一)。手册按 v3 写;任何「DO 混音 / DO 跑音频」的旧描述都已失效。
