# 委派

> 一个 bot 不必什么都自己扛。当一件事更适合别的智能 / 别的人时,它能**委派出去**:换个更强的模型算一道难题,或者私下去问一个真人好友。这套能力让 bot 像个有人脉、知道何时该求助的人。相关:[bot 社交图](bot-social-graph.md)(好友从哪来) · [主动性](proactivity.md)(主动问询是主动性的一种)。

**逻辑**

bot 跨自己边界求助,有两条不同性质的路径:

- **`delegate_to_specialist` —— 换个模型来算。** bot 把一个**自包含的任务**连同一个**模型标识**(如 `claude-opus-4.7`、`~google/gemini-2.5-pro`)交出去,系统用那个模型跑**一次性的、独立的**补全,把答案带回来。专家**看不到 bot 的对话历史**——bot 必须把专家需要的全部上下文、约束、产出格式都写进 prompt 里。专家这一跑没有工具、不开子会话、不依赖任何 bot 关系。**该用哪个模型,由 bot 自己根据它订阅的技能(skill)判断**——技能正文里会写「遇到复杂数学,用 model='claude-opus-4.7' 委派」之类。
- **`ask_friend` —— 私下去问一个真人。** 公有 bot 主动给它的某个**人类好友**发一个自包含的问题。这是**异步**的:工具把问题投递进「bot↔那位好友」的一对一会话(作为一条 bot 消息 + 推送通知),立即返回——对方什么时候看、什么时候回不由 bot 掌控。等 bot 在那边和好友聊清楚、有了答案,再调 `submit_inquiry_answer` 把答案**带回**最初发问的那个会话(这就是「回流」)。

`ask_friend` 因此天然分两阶段:**投递阶段**(发出去、开一个待办记录、返回)与**回流阶段**(收尾、把答案送回发起方)。回流时按「发起方会话当前是否活跃」二选一:活跃(最近有消息)→ 把答案**融进发起方下一句回复**,不单独冒泡;不活跃 → bot **主动开口**,在发起方会话里直接发一条带答案的消息 + 推送。

**为什么**

- **两条路径对应两种「求助」**:一种是「这题我自己的模型不够好,换个脑子」(纯算力 / 能力问题,委派给模型);一种是「这事得问个知道的人」(信息在某个真人那里,问好友)。把它们分成两个工具,语义清楚、各自的约束也不同。
- **委派为什么改成「给模型 slug」而不是「问另一个 bot」**:早期 `delegate_to_specialist` 是「叫另一个 bot 来帮忙」,依赖 `user_bot_contacts`、要开子会话、私有 bot 用不了。重写后它只是「对任意模型跑一次补全」——更简单、更通用、**私有 bot 也能委派**,不再背 bot 关系的包袱(详见文末「注意」)。
- **`ask_friend` 为什么只给公有 bot**:私有 bot 只有一个好友——owner,而 owner 正是它在对话的这个人,「问 owner」就是「直接跟你说话」,没有委派的意义。所以这套工具按可见性门控,只对公有 bot 开放。
- **回流为什么分活跃 / 不活跃**:朋友帮你问到了答案,如果你正在聊天,他会自然地接着话头告诉你(融进回复);如果你已经走开了,他会主动开口提醒你(冒泡 + 推送)。这两种节奏对应真人社交里的两种「带话回来」,避免该插话时突兀冒泡、该提醒时却闷不吭声。

**用在哪·长什么样**

- 这两个都是**给 bot(LLM)用的工具**,用户不直接调;用户看到的是结果——一个更靠谱的答案、或 bot 主动转述的「我帮你问了小李,他说…」。
- `ask_friend` 在好友那一侧的呈现就是一条**正常的 bot 消息 + 推送**:那位好友会收到这个 bot 给他发的问题,在自己的时间回。
- 委派对用户基本透明(可能在 thinking / 工具痕迹里看到「委派给 X 模型」),产物直接体现在回复质量上。

**示例** — 你问公有 bot「老张」一道很硬的数学题,「老张」的技能正文告诉它这种题该 `delegate_to_specialist(model='claude-opus-4.7', ...)`,它把题目和要求完整写进 prompt 交出去,拿回结果融进给你的回答。另一次,你问它一件只有你朋友小李清楚的事——「老张」用 `ask_friend` 私下给小李发了条消息,然后回你「我去问下小李」;过了俩小时小李回了,「老张」在和小李的对话里 `submit_inquiry_answer` 收尾:如果你这会儿正和「老张」聊着,答案会自然出现在它下一句回复里;如果你早走开了,它会主动给你发一条「问到了,小李说…」。

**边界**

- **委派的专家是无状态的、无工具的一次性补全**:不开子会话、看不到历史、不能反过来调工具、不与任何 bot 身份绑定。要它知道的全得写进 prompt。
- **`ask_friend` 只能问 bot 的真人好友**,且按 display name 精确匹配;重名会被拒(目前不接受用 id 指定)。同一个好友身上同时只能挂一个未回的问询——前一个没回完不能再问。
- `submit_inquiry_answer` 必须由**同一个 bot**、从**它当初投递去的那条 relay 会话**里调用,带正确的 `inquiry_id`;跨会话 / 跨 bot 滥用会被拒。
- 这些都是 bot↔bot / bot↔人的**委派**,不是「bot 加 bot 好友」——[社交图](bot-social-graph.md)里没有 bot↔bot 边。

**注意**

- ⚠️ **`delegate_to_specialist` 已被重写,语义变了。** 老 spec / 老注释说它是「问另一个 bot」(开子会话、依赖联系人、私有 bot 不可用)——**那是旧实现,别按它写**。现状:它是「对任意模型 slug 跑一次独立补全」,对所有 bot 常开,不碰 `user_bot_contacts`。
- ⚠️ **`talk_to_bot` 不是当前代码里的工具。** 早期心智里有「bot 直接找另一个 bot 对话」这类设想,现状的两条委派路径是 `delegate_to_specialist`(给模型)和 `ask_friend`(给真人好友)——别把 `talk_to_bot` 当现存能力写进文档。
- `ask_friend` 的好友匹配按名字、且要求名字出现在 bot 本回合的社交圈快照里——这把它和 [社交图](bot-social-graph.md) 绑在一起,问询能问谁取决于 bot 当前的好友集。
- board 的工具页可以整体禁用某个工具(kill-switch),所以「常开」是默认态,不是不可关。
