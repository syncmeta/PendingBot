# 群权限矩阵

[群账号](group-accounts.md)的成员怎么分权。核心是一句话:**三级固定角色,α 版不可自定义。**

**逻辑** —— 群账号成员有三级 role:**`owner` / `admin` / `member`**,每档能干什么写死在下面这张表里。

| 操作 | owner | admin | member |
|---|---|---|---|
| 在群下任一 crew 里对话 / 看摘要 | ✅ | ✅ | ✅ |
| 创建群下的 crew | ✅ | ✅ | ✅ |
| 删除群下的 crew | ✅ | ✅ | 仅自己创建的 |
| **群钱包充值** | ✅ | ✅ | ✅ |
| 加 / 踢 member | ✅ | ✅ | ❌ |
| 启动 / 销毁云端 machine | ✅ | ✅ | ❌ |
| 创建 / 删除 captain bot | ✅ | ✅ | ❌ |
| 批准外部 crew 认本群下 crew 为父 | ✅ | ✅ | ❌ |
| 接受跨主体协作邀请(本群被拉进别人的 crew) | ✅ | ✅ | ❌ |
| **登录代表群账号**(扫码到 PendingCrew Mac/iPad) | ✅ | ✅ | ❌ |
| 加 / 踢 admin、转让 ownership、解散群 | ✅ | ❌ | ❌ |

**为什么 —— α 版固定三档** —— 不做精细 RBAC,就三档,每档能干什么是写死的。这样产品简单、不容易把权限配错;自定义 RBAC 是 v1.x 以后的事。把权限收成固定角色,也让"谁能批准高风险操作"这件事在产品里始终有确定答案。

几条值得单拎出来的约束:

- **单 owner** —— v1 不做 multi-owner。继承 / 交接的场景用"转让 ownership"解决就够了,不需要多个 owner。
- **充值对全员开放** —— owner / admin / member **都能**往群钱包充值。这是有意的:群账号本就是大家合伙出钱,谁都能添。
- **无提现** —— 充进群钱包的钱**不能当现金提出来**。这是为了规避"金融服务"性质的合规风险,同时简化产品。schema 里不留提现接口。
- **群账号永远走 unified billing** —— 群账号**没有 BYOK 概念**,费用一律走平台统一计费。BYOK 只活在 PendingCrew 未登录的本地场景。
- **"登录代表群账号"收在 admin+** —— member 即使知道群账号存在,也**不能**扫码代表它登录 PendingCrew 去跑本机 agent。原因见下面"用在哪",细节见 [设备授权](device-grant.md)。

**用在哪·长什么样** — 群成员管理出现在群账号设置里(加 / 踢人、升降 admin、转让、解散),由服务端强制角色。其中"登录代表群账号"这一行最值得注意:扫码登录会在一台物理设备上打开"以该 subject 跑本机 coding agent"的通道,这是比"在群里发消息"高一档的能力,所以收在 admin+。member 能在群下的 crew 里花群钱包做事,但不能"以群的身份"在一台新设备上铸出一个控制凭据。

**边界**
- **不做自定义 RBAC** —— 就三档固定权限,自定义权限是 v1.x。
- **不做 multi-owner** —— 单 owner;交接用转让 ownership。
- **不做现金提现** —— 群钱包的钱不能提现成现金(份额内部退回不算,见下"注意")。

**注意**
- **自定义权限布尔位是已废的旧设计** —— 早期 schema 在群成员行上散布过 `can_manage_wallet` / `can_manage_runners` / `can_create_crew` 三个布尔位(可自定义权限的雏形)。α 版已收紧成固定三级 role;这些布尔位留作 legacy 数据、不再扩展也不删(删了老 RPC 路径会断),但**它们不是现在的权限模型**,别按布尔位理解或写回。变更出处见 [`subject-foundation.md` Spec v2 §4](../../../superpowers/plans/2026-05-24-subject-foundation.md)。
- **"无提现" vs 代码里的 `/withdraw`,是两件事** —— "无提现"指**不能把钱当现金提到银行卡**。但成员退群 / 群解散 / 部分取出时,会按出资份额把对应额度退回各人的**平台内个人余额**(PNC)——这是平台内部的份额结算,不是现金提现。edge 确实有 `/v1/group-subjects/:id/withdraw`、`/leave`、`/dissolve` 端点,它们退的都是个人 PNC 余额,别因为看到 `/withdraw` 就以为破了"无提现"红线。份额结算的规则归 [`group-pledge`](group-pledge.md)。
- **权限由服务端 RPC 强制,不在客户端** —— 角色检查在 `SECURITY DEFINER` 的 `grp_*` RPC 里,客户端只是触发;别在客户端复刻角色判断当作权威。
