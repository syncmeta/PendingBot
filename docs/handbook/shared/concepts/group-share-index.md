# 群池份额(share index)

**一句话:群里的实缴池不为每笔消费记成员账,而是用一个随池子等比缩小的数(`share_index`)来记谁该拿回多少 —— 你注资时抄下这个数,退出时拿它跟当前值比一比,中间发生过多少笔消费、多少人进出,都不用管。**

这一篇只讲**实缴池的份额数学**。两种出钱姿势(实缴 / 认缴)和它们的产品规则见 [`group-pledge`](./group-pledge.md);群钱包本体见 [`wallet-pnc`](./wallet-pnc.md)。

---

## 逻辑 —— 两个数,三个动作

**存两个数就够了:**

| 存在哪 | 字段 | 是什么 |
|---|---|---|
| `group_pools`(每群一行) | `total_remaining_pnc_micros` | 池子里还剩多少 |
| | `share_index` | 一个比例因子,建池时 = 1 |
| `group_contributions`(每笔注资一行) | `contributed_pnc_micros` | 这笔投了多少 |
| | `share_index_at_join` | **投的那一刻,`share_index` 是多少** |

**任何时刻,一笔注资现在能拿回多少:**

```
可取额 = floor( contributed × 当前 share_index / share_index_at_join )
```

**三个动作各自动什么 —— 这张表是整篇的核心:**

| 动作 | 池子余额 | `share_index` | 谁的 `contributed` |
|---|---|---|---|
| **注资** | + 注资额 | **不动** | 新增一行,记下当时的 index |
| **群里花钱** | − 消费额 | **等比缩小**:`新 = 旧 × 新池子 / 旧池子` | 不动 |
| **取出 / 退群** | − 取出额 | **不动** | **只缩取出者自己的**,按 `(份额−取出)/份额` 等比缩 |

> **花钱动 index(所有人一起承担),取出动自己的 `contributed`(只影响自己)。**
> 这两句是这套模型最容易搞反的地方,记住它,其余都能推出来。

---

## 为什么 —— 一个数换掉一本账

**不这么做的话,每笔群消费都得给每个有份额的成员写一行"你摊了多少"。** 群越活跃、人越多,这本账增长得越快,而它唯一的用途只是回答一个问题:**这个人现在能拿回多少。**

份额模型把这本账压成了一个数:

- **消费只写一行。** 一笔 AI 调用只更新池子那一行(余额 + index),**不碰任何成员记录**。
- **公平性是算出来的,不是记下来的。** 谁承担了哪一段历史消耗,由「你入场时的 index」和「当前 index」的比值自动决定。
- **后来的人不替之前的消费买单。** 新成员注资时抄下的是**已经被压低过的** index,两个 index 一约就抵消了他入场前的所有消耗 —— 这一条不需要任何额外逻辑,是公式自带的。

(这就是 [`group-pledge`](./group-pledge.md) 里提到的 DeFi 质押池记账方式:池子里的资产变化由所有份额持有者按比例承担,份额本身不变,变的是每份额对应多少资产。)

---

## 用在哪·长什么样

- **群钱包页**上每个成员看到的「可取额」,就是上面那个公式的结果。
- **`/withdraw`(部分取出)**:能取的上限 = `min(你要的, 你当前份额, 池子余额)`。
- **`/leave`(退群)** = 一次把自己的份额全额取完。
- **`/dissolve`(解散)** = 所有人按各自份额一次结清。

取出的钱**退回个人 PNC 余额**(平台内部),不是提现到银行卡 —— 见 [`group-pledge`](./group-pledge.md) 的边界一节。

实现在:份额公式 `apps/edge/src/billing/share-index.ts`(22 行,一个纯函数);
三个动作各自的原子 SQL 是 `apply_group_contribution` / `apply_group_pool_spend` / `apply_partial_withdraw`。

## 示例 —— 一个群,从零到有人取钱

金额用 PNC 写(代码里实际是 micros,整数)。

### 第一步:两个人注资

小张投 60,小李投 40。**注资不改 index。**

```
池子 100   index 1
小张  contributed 60  join_idx 1  → 可取 60 × 1/1 = 60
小李  contributed 40  join_idx 1  → 可取 40
```

### 第二步:群里花掉 20

```
index = 1 × 80/100 = 0.8        池子 80

小张 可取 60 × 0.8/1 = 48       (摊了 12 = 20 × 60/100 ✓)
小李 可取 40 × 0.8/1 = 32       (摊了  8 = 20 × 40/100 ✓)
```

**两行成员记录一个字没改**,可取额自己就缩了。

### 第三步:小王这时才进来,投 50

他抄下的 `join_idx` 是**当前的 0.8**,不是 1。

```
池子 130   index 0.8

小张 48    小李 32    小王 50 × 0.8/0.8 = 50
```

**小王一分钱都没替之前那 20 买单** —— 两个 0.8 一约就抵消了。这是公式自带的,没有为它写任何特判。

### 第四步:再花 13

```
index = 0.8 × 117/130 = 0.72    池子 117

小张 60 × 0.72     = 43.2       (摊了 4.8 = 13 × 48/130 ✓)
小李 40 × 0.72     = 28.8       (摊了 3.2 = 13 × 32/130 ✓)
小王 50 × 0.72/0.8 = 45.0       (摊了 5.0 = 13 × 50/130 ✓)
```

三个人**按当下占比**分摊,分毫不差 —— 而这一步同样只写了池子一行。

### 第五步:小张取出 20(人还在群里)

**取出不动 index,只缩他自己的 `contributed`:**

```
小张当前份额 43.2,取走 20 → 缩放系数 = (43.2 − 20) / 43.2 = 0.5370…
小张 contributed: 60 → 60 × 0.5370… = 32.22

池子 117 − 20 = 97

校验:小张 32.22 × 0.72/1 = 23.2   (＝ 43.2 − 20 ✓)
      小李 28.8   小王 45.0        (两人一个数都没变 ✓)
      23.2 + 28.8 + 45.0 = 97      (＝ 池子 ✓)
```

**别人的可取额完全不受影响** —— 因为他们的 `contributed` 和 index 都没动,而池子正好少了小张拿走的那一份。

## 边界 —— 明确不做

- **这套只管实缴池。** 认缴(pledge)不进份额模型 —— 认缴的钱从没进过池子,群消费时实时从各人个人钱包直扣,没有份额、也没有衰减。
- **不做提现。** 份额结算只在平台内部:群池 ↔ 个人 PNC 余额。
- **不为每笔消费保留成员级明细。** 这是有意的取舍:换来的是"活跃群不会把账本撑爆"。要审计具体某一笔谁摊了多少,靠的是消费流水 + 当时的 index,不是成员账。

---

## 注意 —— 坑 & 容易混淆的点

- **⚠️ "取出"不改 index。** 最容易犯的错是以为取出也该像消费一样压低 index —— 那会让**其他人的可取额一起缩水**,等于替他的取出买单。正确做法是缩他自己的 `contributed`,别人一个数都不动。

- **⚠️ 一律用 `floor`,不用四舍五入。** 可取额向下取整,保证**所有人的可取额之和永远不超过池子**。丢掉的零头(micros 级)留在群里,任何现实规模下都可忽略。反过来用 `round`/`ceil` 就可能出现"大家都来取,最后一个取不到"。

- **池子归零时 index 重置为 1。** 否则 index 会一路趋近 0,后续注资的比值会失真。归零重置之后,老注资的可取额算出来是 0(本来也该是 0)。

- **两个动作都在行锁里做。** `apply_group_pool_spend` / `apply_group_contribution` 都先 `select … for update` 锁住池子那一行,再改 —— 并发消费不会算错 index。

- **`share_index` 是 `numeric(40,20)`,不是浮点。** 20 位小数是为了让长期反复衰减不丢精度;用 float 会在几千笔消费后开始漂。

- **池子余额是"公平性镜像",不是唯一事实源。** 真正的余额事实源在 Polar;池子这行同时承担份额衰减的基数。两者偏差超过 1 PNC 会报警 —— **只报警不自动改写**,因为自动改写会让余额和份额失配。
