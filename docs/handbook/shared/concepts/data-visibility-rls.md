# 数据可见性(RLS as capability)

大绿豆怎么决定"谁能看到什么"。这是一条贯穿全产品的隐私底线,不是某个功能的局部规则。头像 / 昵称这条具体路径有专篇 [头像 / 昵称可见性](avatar-visibility.md),本篇讲**一般模型**,不重复头像细节。

**逻辑** —— 两层叠在一起:

1. **RLS 作为统一可见性模型** —— 数据库行级安全(Row-Level Security)是"谁能看哪行"的统一事实源。一个 subject / 用户能不能读到某条记录,由该表的 RLS 策略决定,而不是由某段应用代码临时判断。可见性内建在数据层,默认收紧。
2. **id-as-capability(id 即凭据)** —— 对于"需要在受限场景里给一点信息"的资源(典型是头像图片字节),手段是让资源的 id **不可枚举**:你只能从合法处(好友查找结果、群成员列表)拿到这个 id,凭它能取到的也仅限**展示所需**的那点东西(图片字节),而非完整 metadata。拿到 id = 有权看这一点点,但拿不到 id 就无从枚举。

合起来:**默认不全局公开**。新增任何"想看到别人 / 别的资源"的需求,要么落到已有的合法路径上,要么明确拒绝 —— 不开第三条全局暴露的口子。

**为什么** —— 这是党纲"社交建立在信任上,不做开放广场""隐私默认收紧"的具体落点。不暴露可被陌生人直查 / 枚举的身份与资源:信息只在"对方已经把自己暴露给这个上下文"(挂了隐私号、同在一个群、是这个 bot 的好友)时才给,且只给最小必需。把可见性建在 RLS + 不可枚举 id 上,而不是建在"应用层记得加 where 条件",是为了让这条底线**默认成立、不靠每处代码自觉**。

**用在哪·长什么样** — 这条模型在产品里以"你看不到陌生人列表"的形式存在:
- **加好友** —— 只有查某人的隐私号(handle)时才看得到对方头像 + 昵称,不做按昵称模糊搜人(见 [加人类好友](../../pendingbot/features/add-friend.md))。
- **群成员** —— 只有和某人同群时才看得到非好友成员的头像 + 昵称。
- **bot 好友圈** —— bot 的好友列表对好友圈内半透明(谁是被谁拉进来的看得见),对圈外不可见(见 [bot 邀请](../../pendingbot/features/bot-invites.md))。
- **责任主体范围** —— crew / 会话 / 钱包的可见性绑 `responsible_subject_id`:谁是这个 subject 的成员,谁才看得见(见 [subject](subject.md))。

**边界**
- **没有全局公开层** —— 不存在"所有登录用户都能读"的身份 / 资源池。曾经存在过(早期头像行的全局 RLS 分支),已被收掉(见 [头像可见性](avatar-visibility.md))。
- **id-as-capability 只服务"展示所需"** —— 凭一个头像 id 取到的是图片字节,不是文件 metadata(`r2_key` 等仍由 RLS 挡住)。这不是一个"拿到 id 就拿到一切"的万能钥匙。

**注意**
- **可枚举资源要配限流** —— 凡是"404-vs-200 能确认存在性"的端点(隐私号查找、群加入码),除了 RLS 还要加限流挡批量枚举(见根 [`CLAUDE.md`](../../../../CLAUDE.md) 的 Edge rate limiting 约定)。RLS 管"能不能读到内容",限流管"能不能反复试探存在性",两者互补。
- **写操作的 RLS 与读分开** —— α 阶段不少表的写只通过 `SECURITY DEFINER` RPC 走(避免精细 write policy 写错),client 直接 INSERT/UPDATE 被关。看到"读得到但写不了"不是 bug,是这个务实选择。
- **别在应用层复刻可见性判断当权威** —— 权威在 RLS / 不可枚举 id;应用代码里的过滤是体验优化,不是安全边界。

**现状** — ✅ 模型已落地并验证:头像 metadata 泄露已关、两条受限路径的头像字节已服务(见 [头像可见性](avatar-visibility.md) 的 D3 验证);隐私号查找带限流;subject 维度可见性随 subject schema 上链。作为一条横切底线,它在加好友 / 群成员 / bot 邀请等已验证功能里持续生效。
