# 客户端读路径

数据库只有一个区(法兰克福),US / Asia 的用户每次首屏都吃一趟跨洋往返。所以**热读路径**不让客户端直连数据库,而是走"边缘投影":数据库退为最终一致的真源,**读放在服务端边缘、客户端只做缓存**。相关:[配置即 CMS](config-as-cms.md) · [群账号](group-accounts.md) · [群权限](group-permissions.md)。

**逻辑(CQRS 读投影)**

- **写回真源,读走边缘** — 任何改真源的写仍然回数据库(法兰克福),即时感来自乐观 UI + worker 快速 ACK,不是数据库变近了。但**最频繁、最延迟敏感的两类读**——会话列表 + 未读、消息尾——不再直连数据库,改读 CF 边缘的**投影**。
- **投影是可重建的派生,永不权威** — 数据库的写触发器发一条 webhook,既扇出实时增量(已有),又顺手把数据物化进边缘投影。投影只是真源的边缘镜像;它丢了 / 冷了,就从数据库重建一次。
- **三层读** — 客户端开屏时:
  - **L1 设备本地缓存**(加密)——即时、离线可用,开屏先渲染。
  - **L2 CF 边缘投影**——10–30ms,追赶真源,替代过去"直连法兰克福"那一跳。
  - **L3 数据库**——跨区、带行级安全,只在边缘没命中 / 深翻历史 / 投影重建时兜底。
- **delta 对账,不傻拉全量** — 客户端报"我本地到第几号修改",边缘投影只回这之后的变更(含撤回 / 编辑的删除标记),不是每次重拉一屏。投影自己维护一个单调的修改号当游标;投影重建时换一个新纪元(epoch),旧游标失效则客户端全量重取一次。
- **两个投影,各管一摊**:每会话一个(消息尾 + 成员名册 + 修改号),每用户一个(会话列表 + 未读 + 修改号)。会话列表只投影**标量列**(谁、什么类型、未读数…),**绝不**把 bot / 对端的头像名字塞进去——否则 bot 一改名就要刷它所有会话行。头像名字这层由客户端拿本地缓存自己 hydrate。
- **本地缓存兜底** — 边缘端点失败 / 为空时,客户端**回落直连数据库 + 行级安全**(冷路径天然安全)。活兜底绝不删——乐观写、去重(client_message_id)那套仍在,投影不破坏它。

**为什么**

- **把数据库移出同步热路径,不是搬空它** — 数据库的角色从"前线、近、同步"变成"真源 + 写入终点 + 身份源 + 喂投影的事件源 + 投影的重建源"。重要性不降,只是不再卡延迟。
- **热路径授权要在 worker 显式重做** — 行级安全是数据库那一层的强制保护;数据搬到边缘后这层自动保护没了,所以热路径的"谁能读这个会话"必须在 worker 代码里显式判(成员 / 属主门),并把数据库行级安全**静默过滤掉的那些行 / 列**(撤回消息、语音通话回顾等)逐条复刻进投影。冷回落保留数据库 + 行级安全 = 免费的第二道防线。
- **存储选型对症** — 每会话 / 每用户的列表 + 未读是"同 key 高频写 + 要强一致(红点要准)",用 Durable Object(单点、强一致);全局只读的配置走 KV(见配置即 CMS);两者不混。

**用在哪·长什么样**

- **用户侧**:开 app 首屏(会话列表 + 红点)、点进一个会话看消息——这两条最高频的读现在走"本地缓存先渲染 → 边缘投影追新"。用户感知到的是首屏更快、跨区不再白屏等待。
- **客户端结构**:三端(iOS / iPad / macOS)共用一个 Repository 门面收口缓存读写,L1/L2/L3 + delta 对账挂在这一层,三端自动继承,不用每端接一遍。

**示例** — 你人在美西,打开 app。本地缓存(L1)立刻把上次看到的会话列表画出来;同时客户端拿"本地到第几号"去问最近的 CF 边缘节点上的用户投影(L2),它只回你离线期间变化的那几行(新消息、未读 +1),10–30ms 追平。你没有等一趟到法兰克福的 200ms 往返。点进某个会话,消息尾同理走该会话的边缘投影。

**边界**

- **只投影两类热读** — 消息尾(每会话)+ 会话列表 / 未读(每用户)。联系人列表、设置、账单日志、来信 feed 这些"频繁但不敏感"或"敏感但不频繁"的读不单独投影,留在 worker→数据库 / 本地缓存。
- **深翻历史不走投影** — 投影只留消息尾(按条数,~200 条量级);往上翻老历史回数据库,靠"滚动意图预取"藏延迟。
- **身份 / 写仍直连或回真源** — 登录 / 注册 / 刷新会话走数据库的 Auth(为客户端直连而设);所有写、所有 RPC、账本审计回真源,绝不让边缘投影当权威。
- **不做端到端加密**(边缘投影需要明文授权 / 服务);不引入多环境(pre-launch 单环境)。

**注意**

- **授权门 ↔ 行级安全的对齐是隐式不变量,无测试守护** — 热路径放不放行,完全靠 worker 授权门;投影内容是绕过行级安全回填的,所以**门是热路径唯一权威**。当前安全是因为"能看见会话行的人正好能看见它的消息",但这个对齐靠人记、没有断言守护:谁以后给会话加一条更宽的读策略却忘了给消息加对应策略,授权门会基于"能看见会话"放行、把全量消息尾喂给一个本不该读的人 → 静默越权,且冷回落不会兜住(热命中根本不经行级安全)。这是结构性根基隐患(见 tech-debt 🔴)。
- **吊销有几秒窗口** — 踢人后,成员名册经 webhook 同步到投影前有几秒,被踢者还能从边缘读。群踢人罕见、几秒可接受,默认走 webhook;要即时需踢人时同步驱逐那个投影对象。
- **盲盒模型 pill 固有一跳** — 会话当前模型态(是否揭示 / 抽中谁)本地无缓存,盲盒会话开屏会从"bot 模型名"跳到"PendingModel / 抽中名",要消除得把会话模型态也落本地缓存(未做)。

**现状** — 🟨 **全链路代码已落地并合 main**(两个投影 DO + webhook 写穿 + 冷回填 + fail-closed 授权门;客户端三端 Repository 收口 + edge-first/数据库 fallback cutover)。**核心尾巴**:① 最终使用路径(iOS / Mac 真机 + 真边缘端点)的 runtime 正确性——投影命中 / delta / 回填 / 2MB 行护栏 / 列表 hydration 视觉——还是纸面,需部署 + 真机冒烟;② 授权门 ↔ 行级安全对齐无测试守护(🔴);③ delta 游标当前实际多走全量(since=0)、富列截断懒取当 nil,属押后优化。配置 → KV 那部分(`/models` 目录缓存等)为 ✅。
