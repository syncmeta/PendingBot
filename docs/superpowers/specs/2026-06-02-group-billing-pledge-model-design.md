# 群计费 —— 实缴池 + 认缴(pledge)统一模型 Design

**日期**: 2026-06-02
**状态**: 已与用户确认模型,待审稿 → writing-plans
**关系**: 扩展并部分取代 `plans/2026-06-02-group-wallet-polar-rehome.md`(实缴池 + share-index + 退款 已落地;本稿新增**部分取出** + **认缴机制**,并收尾链式退款/漂移)。底座沿用 `specs/2026-06-01-billing-engine-design.md`(Polar=余额事实源,WalletDO=边缘缓存)与 `billing-v2-design.md §9`(share-index 质押池)。

---

## 1. 目标 / 用户初衷

- 群计费不需要人工频繁分配额度;**额度自动流向需要扣的地方**。
- **一份个人余额可复用于多个群**(OpenRouter 式:一个余额到处用,先到先得)。
- **一个人欠费不拖垮整个群**。
- 群里能实时看到每个人当前的**分摊比例 = 可取出比例**(同一个数:你在群里的实时占比)。
- 钱永不提现成现金;"取出"= 退回个人 PNC 余额。

## 2. 核心模型(一句话)

**每个群一个钱包 + 一套 share-index 账;群层面不区分认缴/实缴(区分在上层)。** 区别只在"钱在哪、何时动":

| 模式 | 钱在哪 | 份额怎么算 | 何时动钱 |
|---|---|---|---|
| **实缴 (deposit)** | 真转进群钱包(Polar) | share-index 注资,`share_now = contributed × 当前idx/join时idx` | 注资时转入;消费时从池扣(idx 衰减) |
| **认缴 (pledge)** | **不动,留个人钱包** | **动态份额 = min(pledge, 个人余额)**,实时 | **消费时**按占比当场从个人钱包直扣(选项 i) |

群的"总份额" `S = 实缴池余额 + Σ认缴成员 min(pledge, 余额)`。每人占比 `p_i = 份额_i / S` —— 这一个数同时是**分摊比例**和(实缴的)**可取出比例**。

## 3. 消费分账(核心数学)

一笔群消费成本 X(vendor 成本,无 markup):

1. 算 `S = 实缴池余额 + Σ认缴成员 min(pledge_i, 个人余额_i)`(认缴成员的余额经其个人 WalletDO 读)。
2. 每人摊 `X·(份额_i / S)`。
3. **实缴部分**(= `X · 实缴池/S`)从群池出:`apply_group_pool_spend(group, X·实缴池/S)` → 池减、`share_index ×= (1 − X/S)`。所有实缴注资人的 `share_now` 同比例缩 = 各自摊了 `X·占比`。✅
4. **认缴部分**:对每个认缴成员,从其个人钱包直扣 `X·(份额_i/S)`(经其个人 WalletDO)。
5. 校验:实缴部分 + 认缴各部分 = X,不重不漏,平台不亏。

> share_index 只服务实缴池;认缴成员没存钱,不进 group_pools,其份额每次从 `group_pledges` + 个人余额实时算。

## 4. 认缴细则

- **份额永远 = min(pledge, 个人余额),实时**。个人余额掉到低于 pledge → 份额自动缩到余额 = **等效实缴取出**(用户 R4)。因为认缴啥都没预存,这条天然成立,无需特殊处理。
- **认缴的人没有"池中可取额"**(没存钱)。他要"退"= **调低 / 取消 pledge**(改授权,不涉及退款)。
- **超额认缴 / 多群复用**:可给 A 群认缴 100、B 群也 100,即使只有 100 余额。谁先消费谁先扣;另一个群下次消费时读到余额已降,该成员份额自动缩。先到先得,允许超额。
- **欠费隔离(R6)**:某认缴成员余额见底 → 其份额(= min(pledge,0) = 0)→ 自动退出本轮分账,`S` 不含他,其余人按占比继续,群照跑。他不欠群钱、不连累别人。
- **扣款时余额不足的竞态**:门禁已按 `min(pledge,余额)` 预算过,正常扣得动;若两个群并发把同一余额扣穿(竞态),个人 WalletDO 串行兜底——后到的那笔读到余额已低、份额已缩,只扣得到的部分;残余缺口由群池吸收或平台自担(有界,记 chargeback_loss),并把该成员标记认缴失效。

## 5. 取出(实缴,随时、可部分)

- 取消"必须静止态"限制 → **随时可取**。依据:share-index 是快照模型 + 群 WalletDO 单线程串行,取出与消费扣款走同一串行入口、各自基于当下 idx/余额原子计算,绝不算错。
- **部分取出** `/withdraw {pnc}`:`金额 ≤ 我当前 share_now`;群池减该金额(`apply_group_refund`)、退回个人 Polar 钱包(grant)、按比例缩小我的 active contributions(`contributed ×= (share_now − 取)/share_now`,join idx 不变),share_index 不变。取完仍在群。
- 全额取出 = `/leave`(已实现)。认缴的"取出" = 调低 pledge(见 §4)。
- 诚实小角:流式回合最终成本要等回合结束才精确,若有人正好流式中途取走,极端下池子在末笔扣款落地时可能短一点点——overdraft 缓冲兜着、新回合本就要过门禁,预发布阶段可忽略,记 tech-debt。

## 6. 门禁(认缴改动)

群门禁不再只读群钱包一个余额:**全群可用 = 实缴池 + Σ认缴成员 min(pledge, 余额)**;一轮消费超出 → 整群进节流/拒绝。需顺带读认缴成员余额(经各自 WalletDO)。每轮多几次 DO 读,预发布可接受;后续可缓存优化。

## 7. 个人 WalletDO = 串行权威(认缴新增的关键机制)

每个用户一个个人 WalletDO,是其余额的强一致事实源。所有动其余额的动作——本人直接消费、多个群的认缴拉取、取出入账——**全部经他这个 DO 串行**,根治"多群并发扣同一余额"的双扣。群 WalletDO 仍存在(管实缴池 + 群消费门禁 + share-index)。即:

- **群 WalletDO**:实缴池余额 + 群消费门禁聚合 + 调 share-index RPC。
- **个人 WalletDO**:个人余额事实源;认缴直扣、取出入账落在这里。

## 8. 数据模型

- 复用 `group_pools`(实缴池 total + share_index)、`group_contributions`(实缴注资快照)、`pnc_ledger`(审计)。
- **新增 `group_pledges`**:`(subject_id, user_id, pledge_pnc_micros, status active|revoked, created_at, updated_at)`,唯一 `(subject_id,user_id)`。RLS:本人读写自己的、群 owner/admin 可读全群。
- 新增原子 RPC:`apply_partial_withdraw`(缩 contributions + 减池)。认缴直扣走个人 WalletDO,不入 group_pools。

## 9. 收尾(之前挂着的尾巴,并入本稿)

- **链式退款命中群注资**:Apple/LS 退款命中已实缴进群的钱 → 按 `share_now` 冲减群池 + 超出平台自担(§9 chargeback_loss)。
- **群池漂移报警**:WalletDO 对账时比对 `group_pools.total` 与 Polar 群余额,超 1 PNC 报警。
- **`/leave` 联动删 membership 行**(目前只退款不删行)。
