# PendingBot — workflow conventions

This file is auto-loaded by every Claude Code session in this repo. Use it together with the user's memory (which already covers worktree-per-session, auto-commit on small units, auto-push of non-main branches, leaving other worktrees' dirty files alone, and the rebase/merge recipes).

## Branch model

- `main` — always-deployable trunk. Never commit straight to `main` for non-trivial work; branch first.
- `feat/<short-name>` — new feature (e.g. `feat/scroll-share`, `feat/bot-invite-flow`)
- `fix/<short-name>` — bug fix (e.g. `fix/bot-invite-handle`)
- `chore/<short-name>` — refactor / cleanup / tooling / migrations renumber
- `claude/<auto-generated>` — what the Claude Code UI auto-creates. **As soon as the scope is clear, rename it**: `git branch -m feat/<name>` (or `fix/`, `chore/`). Don't let auto-names live past the first commit or two.

Names are short, kebab-case, English (the repo's commit prefixes are English: `edge:`, `ios:`, `db:` — match that).

**Renaming detail:** `git branch -m` only renames the branch. The worktree directory stays at the original `.claude/worktrees/<random>/` path — that's fine, it's an internal location and `git worktree remove <path>` still works after the branch rename. Don't bother running `git worktree move` unless the user explicitly asks; the cosmetic mismatch isn't worth the extra step.

## Worktree layout

One worktree per branch, under `.claude/worktrees/<branch-tail>/`. The tail is everything after the prefix slash (`feat/scroll-share` → `.claude/worktrees/scroll-share/`). `.claude/` is gitignored, so worktrees don't pollute the tree.

Manual creation when needed:
```
git worktree add .claude/worktrees/<tail> -b <prefix>/<tail> main
```

## Merging back to main — pick by size

Run from the feat worktree first to sync:
```
git fetch origin
git rebase origin/main          # if branch was never pushed
# OR: git merge origin/main     # if branch is already on remote
```

Then judge size with:
```
git log main..<branch> --oneline | wc -l
git diff --stat main...<branch>
```

- **≤2 commits AND change is focused** → linear merge:
  ```
  git checkout main
  git merge --ff-only <branch>
  ```
- **Multi-commit feature / cross-cutting change** → preserve the feature boundary with a merge commit:
  ```
  git checkout main
  git merge --no-ff <branch> -m "Merge <branch> — <one-line what it does>"
  ```

Never squash-merge — it destroys the small-unit commit history we deliberately keep.

## Pre-merge checks

Before merging into `main`, run typecheck on whatever was touched:

- Edge changes: `bun --filter='@pendingbot/edge' run typecheck`
- iOS changes: `cd apps/ios && xcodebuild -project PendingBot.xcodeproj -scheme PendingBot -configuration Debug -sdk iphonesimulator build` (or whatever scheme the user has wired)
- Migrations: ensure file numbering is contiguous and the latest migration number matches `supabase/migrations/`

If typecheck fails, fix on the branch and re-commit; don't merge red.

## Before writing a new migration — claim a number from the registry

Multiple parallel sessions routinely land migrations at the same time, so "look at `ls supabase/migrations/` and pick max+1" deadlocks two sessions onto the same number. Use [`supabase/migrations/REGISTRY.md`](supabase/migrations/REGISTRY.md) as the canonical claim list:

1. Read `REGISTRY.md` — the `Last assigned` line and the `Reserved (unmerged branches)` table tell you the next free number.
2. Defense in depth — also run `git fetch --quiet && git log --all --name-only --pretty=format: -- 'supabase/migrations/*.sql' | grep -oE '00[0-9]+' | sort -u | tail -5` and pick higher than anything you see, in case a sibling session pushed without updating the registry.
3. In the **same commit** as the new migration, update `REGISTRY.md`: bump `Last assigned`, append the row to `History`, and if the branch is unmerged also add it to `Reserved` (drop that row when the branch lands on main).
4. Auto-push will publish the reservation; sibling sessions then see it via `git fetch`.

If a collision happens anyway (both sessions claimed before either pushed), the loser renumbers on their branch with a `chore(db): renumber 00NN → 00MM` commit before merging.

## After applying a migration

Anything that lands a new file under `supabase/migrations/` is only half done — once the user has applied it (Supabase Studio / `supabase db push` / however they sync), the TypeScript schema needs to be regenerated so edge code that references new tables/columns typechecks:

```
supabase gen types typescript --local --schema pendingbot \
  > apps/edge/src/db/schema.ts
```

(Or `--linked` instead of `--local` if pulling from the linked project; the `apps/edge/src/db/schema.ts` header documents the exact command.)

If you (the agent) are the one running it: run that command, then re-run `bun --filter='@pendingbot/edge' run typecheck` and commit the regen as a separate `chore(db): regen schema.ts after 00NN` commit.

If the user is running it: tell them in the wrap-up which migration they need to apply and that schema.ts regen + edge typecheck go together. Don't claim a feature is done if it depends on a not-yet-applied migration.

## Cleanup after merge

```
git worktree remove .claude/worktrees/<tail>
git branch -d <branch>          # -d, not -D — refusal means there are unmerged commits, investigate
```

Pre-launch (no users yet): after merging into `main`, push it yourself with `git push origin main`. Re-add the "user pushes main themselves" gate after launch.

## Deploys

- Edge: `bun --filter='@pendingbot/edge' run deploy` — single deployed env (`env.production` in `wrangler.jsonc`); local iteration uses `wrangler dev`. The `--filter='...'` form (with `=`) matters — bun ≥ 1.3 silently mis-parses `--filter @pendingbot/edge` (space-separated) as no-match.
- iOS: TestFlight via the configured ASC API key (see user memory)

Don't auto-deploy on merge — deploys are deliberate and user-initiated.

Full deploy recipe (Board, Edge secrets, DB push, seed apply, post-merge checklist, gotchas) lives in `docs/deploy.md` — read that file when the session is actually about deploying, not on every session.

## First action on every session that's about to change code

Before touching files, check where you are:

```
git branch --show-current
pwd                            # main worktree or .claude/worktrees/<x>?
```

Three cases:

1. **You're in a `claude/<auto>` branch in a worktree** → user just opened a fresh session via the UI. Read their first concrete instruction, derive a branch name (`feat/<name>` / `fix/<name>` / `chore/<name>`), and run `git branch -m <new-name>` before the first commit. If the instruction is too vague to name yet (e.g. "看看 X 是怎么实现的"), leave the rename until scope is clear or until the first edit.

2. **You're already on a `feat/*` / `fix/*` / `chore/*` branch in a worktree** → continue on it unless the user clearly switches topic. If they switch topic, suggest finishing/parking the current branch first rather than mixing scopes.

3. **You're in the main worktree on `main`** → for any code change, do NOT commit to `main`. Either:
   - **(preferred)** look up existing branches with `git branch -a | grep -E '(feat|fix|chore)/'` and `git for-each-ref --sort=-committerdate refs/heads/`, scan for one matching the topic; if a match exists, tell the user the path and ask them to open a session there.
   - **(fallback)** create a new worktree+branch with `git worktree add .claude/worktrees/<tail> -b <prefix>/<tail> main`, then tell the user "open a new session in `.claude/worktrees/<tail>` to continue" — current session can't move into it.
   - The main-worktree session itself stays in read-only / planning / status-check mode.

Inferring `feat/` vs `fix/` vs `chore/` from the user's phrasing:
- "加 / 实现 / 新功能 / add / implement / new" → `feat/`
- "修 / fix / bug / 不对 / 报错" → `fix/`
- "重构 / 清理 / 改名 / refactor / cleanup / rename / 整理" → `chore/`
- Ambiguous → ask once, in one short question.

## When user says...

- "开个 feat/foo" / "start a feature" → if not already in a worktree, create worktree + branch off `main`, tell the user the path to open a new session in
- "改 X 功能 / 修 Y bug" without naming a branch → run the "First action" decision tree above
- "把分支合回 main" / "merge this back" → fetch, judge size, run the right merge variant, typecheck, clean up worktree+branch, remind about `git push origin main`
- "清一下 stale worktree" / "clean stale worktrees" → list with `git worktree list`, check each with `git rev-list --count main..<branch>`. Zero-commit ones can be force-removed; non-zero ones get listed for the user to decide.
- "把当前分支改名" → `git branch -m <new-name>` from inside the worktree
