## Branch model

- `main` — always-deployable trunk. Never commit straight to `main` for non-trivial work; branch first.
- `feat/<short-name>` — new feature (e.g. `feat/scroll-share`, `feat/bot-invite-flow`)
- `fix/<short-name>` — bug fix (e.g. `fix/bot-invite-handle`)
- `chore/<short-name>` — refactor / cleanup / tooling / migrations renumber
- `claude/<auto-generated>` — what the Claude Code UI auto-creates. **As soon as the scope is clear, rename it**: `git branch -m feat/<name>` (or `fix/`, `chore/`). Don't let auto-names live past the first commit or two.

Names are short, kebab-case, English (the repo's commit prefixes are English: `edge:`, `ios:`, `db:` — match that).

**Renaming detail:** `git branch -m` only renames the branch. The worktree directory stays at the original `.claude/worktrees/<random>/` path — that's fine, it's an internal location and `git worktree remove <path>` still works after the branch rename. Don't bother running `git worktree move` unless the user explicitly asks; the cosmetic mismatch isn't worth the extra step.

## Worktree layout

One worktree per branch, under `.claude/worktrees/<branch-tail>/`. The tail is everything after the prefix slash (`feat/scroll-share` → `.claude/worktrees/scroll-share/`). `.claude/` is gitignored, so worktrees don't pollute the tree.

Manual creation when needed:
```
git worktree add .claude/worktrees/<tail> -b <prefix>/<tail> main
```

## Merging back to main — pick by size

Use local `main` as the source of truth. The user is the only developer; `origin/main` is only a backup remote, not the merge base for normal work. Do **not** run `git fetch origin` or rebase/merge against `origin/main` as part of the routine merge-back flow unless the user explicitly asks to sync with remote.

Run from the feature worktree first to sync with local `main`:
```
git rebase main                 # if branch was never pushed
# OR: git merge main            # if branch is already on remote
```

Then judge size with:
```
git log main..<branch> --oneline | wc -l
git diff --stat main...<branch>
```

- **≤2 commits AND change is focused** → linear merge:
  ```
  git checkout main
  git merge --ff-only <branch>
  ```
- **Multi-commit feature / cross-cutting change** → preserve the feature boundary with a merge commit:
  ```
  git checkout main
  git merge --no-ff <branch> -m "Merge <branch> — <one-line what it does>"
  ```

Never squash-merge — it destroys the small-unit commit history we deliberately keep.

## Pre-merge checks

Before merging into `main`, run typecheck on whatever was touched:

- Edge changes: `bun --filter='@pendingbot/edge' run typecheck`
- Edge tests: `cd apps/edge && ./node_modules/.bin/vitest run` (vitest tests sit under `apps/edge/src/lib/*.test.ts` + `apps/edge/tests/*.test.ts`)
- iOS / iPad / macOS changes: `cd apps/pendingbot && xcodebuild -project PendingBot.xcodeproj -scheme PendingBot -destination 'generic/platform=iOS Simulator' build`（Mac 端：`-destination 'platform=macOS'`）。改 `project.yml` 后跑 `xcodegen` 再编译。
- Migrations: new files use a timestamp prefix (see "Before writing a new migration" below); legacy 4-digit files are fine left as-is

If typecheck fails, fix on the branch and re-commit; don't merge red.

## Deferred device QA — batch the human checks

Do not make every small session wait for the user to run real-device QA. Split the gates:

- **Merge gate**: run the strongest automated/local checks available for the touched surface (typecheck, unit tests, `xcodebuild`, simulator build). If those are green and the change is focused/conflict-free, commit and merge by the normal rules.
- **Human QA gate**: flows that need a signed real device, OAuth provider UI, shared Keychain/App Group behavior, QR camera scanning, push/deep links, or visual/interaction judgment become an explicit "pending device QA" tail. Record the exact scenarios to verify instead of blocking the small branch on the user.
- **Completion semantics**: implementation may be "merged, pending device QA", but the task/roadmap item is not `completed` until that human QA passes. Keep it open, annotate it, or record the tail in `docs/tech-debt.md` / `docs/progress.md` as appropriate.
- **Batch validation**: after a batch of related branches lands, run one consolidated device QA pass from local `main` and close all covered tails together. Prefer one real-device build that exercises the integrated surface over many tiny builds for isolated fixes.
- **Escalate only when needed**: if a change cannot be meaningfully protected by automated checks and could break login, billing, migrations, data loss, or app launch, call out the risk and wait for a deliberate QA/deploy decision.

## Pre-commit hook (lefthook)

This repo ships a `lefthook.yml` with a `pre-commit` block that runs two checks in parallel:

1. **schema-regen-check** — if any `supabase/migrations/*.sql` file is in the staged set, refuse the commit unless `apps/edge/src/db/schema.ts` is also staged. Stops the "migration landed, schema.ts forgotten" pattern.
2. **typecheck-edge** — runs `bun --filter='@pendingbot/edge' run typecheck` whenever `apps/edge/src/**/*.ts` or `packages/identity/src/**/*.ts` is staged. Cheap (~3s) and saves a CI round-trip.

Install (once per clone):
```
bunx lefthook install
```

If your `git config core.hooksPath` is already set globally, `lefthook install` will warn; `bunx lefthook install --reset-hooks-path` clears the override (don't run this blindly if your global hooks do important things). The repo's `package.json` includes `"prepare": "lefthook install"`, so a fresh `bun install` after clone will set it up.

Escape hatch for emergencies: `LEFTHOOK=0 git commit ...` skips all hooks for that one commit. Use this when the schema-regen check trips on a comment-only edit to a migration file (the check is intentionally coarse — it watches the path, not the content).

## Edge HTTP error envelope

Every non-2xx response from `/v1/*` goes through `apps/edge/src/lib/http-error.ts:jsonError(c, status, code, opts?)`. Wire shape:

```ts
{ error: { code: ApiErrorCode, message?: string, detail?: unknown } }
```

- `code` is a stable snake_case identifier from the `ApiErrorCode` union — adding a new code = adding to the union in `http-error.ts`. iOS branches on `err.code` via `APIError.http(status:code:message:body:)`.
- `message` is human Chinese copy when the route has one; iOS surfaces it as-is.
- `detail` is free-form structured payload (e.g. `{ quota_bytes, used_bytes }` for `quota_exceeded`).

Don't fall back to bespoke `c.json({ error: 'foo' }, 400)` shapes — the typed envelope is what iOS expects.

## Edge rate limiting

For endpoints that expose an enumerable resource (handle lookups, group join codes, anything where a 404-vs-200 confirms existence), gate via the Cloudflare native ratelimit binding:

1. Declare the binding in `apps/edge/wrangler.jsonc` under `env.production.ratelimits` (or the top level for the default env). Use distinct `namespace_id` per logical bucket.
2. Add the binding to `Env` in `apps/edge/src/types.ts` typed as `RateLimit`.
3. At the top of the handler, call `await rateLimitOrBlock(c, c.env.YOUR_LIMITER)`; return the `Response` directly if non-null.

Key resolution defaults to `c.var.userId` → `CF-Connecting-IP` → `'anon'`, so logged-in users get per-user buckets and pre-auth paths bucket by IP.

## Before writing a new migration — use a timestamp prefix

Parallel worktree sessions can't reliably coordinate on a 4-digit sequential number (each branch only sees what's been merged), so new migrations use a UTC timestamp prefix — `YYYYMMDDHHMMSS_<short_name>.sql` — which is collision-free by construction. Generate with the supabase CLI:

```
supabase migration new <short_name>
```

This writes `supabase/migrations/<timestamp>_<short_name>.sql`. Two sessions run a second apart get distinct filenames and never fight.

Legacy `0001`–`0061` files stay as-is — supabase applies migrations in lexicographic order and `00xx` < `20xx`, so the legacy block keeps running first. Don't bulk-rename them; only renumber if a collision in the legacy space ever needs untangling.

If you can't run `supabase` for some reason (e.g. seed-style migration drafted by hand), grab the prefix with `date -u +%Y%m%d%H%M%S` and create the file directly. Don't pick numbers manually.

## After applying a migration

Anything that lands a new file under `supabase/migrations/` is only half done — after applying it, the TypeScript schema needs to be regenerated so edge code that references new tables/columns typechecks:

```
bun --filter='@pendingbot/edge' run types:db
```

The script wraps `supabase gen types typescript --linked --schema pendingbot 2>/dev/null > src/db/schema.ts`. **The `2>/dev/null` matters**: the supabase CLI emits "new version available" notifications to stdout (not stderr alone), which would otherwise corrupt schema.ts. Use the script, don't invoke the bare command — past sessions have lost time to that footgun.

Apply order (the agent does this, not the user):
1. `supabase db push --linked` (from the main worktree dir; that's where `supabase/.temp/linked-project.json` lives)
2. `bun --filter='@pendingbot/edge' run types:db`
3. `bun --filter='@pendingbot/edge' run typecheck`
4. Commit the regen as `chore(db): regen schema.ts after <migration_name>`

## Keep an eye on project health — log structural issues to `docs/tech-debt.md`

While doing normal work, stay alert for problems that undermine the project's foundation, not just the task in front of you. When you notice one, **record it** in `docs/tech-debt.md` (the structural-risk register). This is passive vigilance during regular work, not a dedicated audit pass — you're not expected to go hunting.

What's worth logging (the register has the full rubric + entry format):

- 🔴 **Foundational** — wrong data models, designs that get worse with scale, hidden cross-module coupling, security / data-consistency hazards, migration-ledger drift. Anything project-wide.
- 🟡 **Rob-Peter-to-pay-Paul** — a fix that makes A work by pushing the cost onto B; workarounds that bypass types/validation/constraints; copy-paste instead of abstraction; "temporary" implementations.
- 🟢 **Non-standard** — code/naming/structure that drifts from this repo's conventions; not fatal but corrodes consistency over time.

Rules:

- **Record, don't auto-fix.** Fixing a foundational issue is usually its own chunk of work that would derail the current task. Append an entry and move on — unless the user asks you to fix it now.
- If *you* introduce a knowingly-temporary or makeshift implementation in the current task, log it too (own the holes you dig).
- Don't log what linter/typecheck already catches, pure style nits, or task-local TODOs.
- Mention any notable new entries in your end-of-turn summary so the user sees them surface.

## 账本维护 — task 系统 / progress / roadmap / tech-debt 必须跟得上代码

项目有四个账本，**各归其位，不混用**。它们靠纪律保持与代码一致；失效从来不是工具的错，是更新与意识没跟上。

| 账本 | 本职 | 粒度 |
|---|---|---|
| **Task 系统**（内置 TaskList） | "做没做"的**事实源** | 单个可提交单元 |
| **roadmap**（`docs/superpowers/plans/2026-05-28-v1-0-implementation-roadmap.md`） | 计划 / 顺序 / 依赖 | phase / T 编号 |
| **`docs/tech-debt.md`** | 结构风险 + 关不掉的尾巴 | 风险条目 |
| **`docs/progress.md`** | 当前真实状态 rollup + 阻塞 + 下一步（串起前三者） | 工作流 / feature |

判断"做没做"以 **Task 系统**为准；判断"整体到哪了"以 **progress** 为准；两者冲突 = 该对账了。

纪律（把更新绑到已经会发生的动作上，别让它成为可遗忘的独立步骤）：

- **小单元 auto-commit 的同一拍**，顺手 `TaskUpdate` 翻对应 task（跟"commit 绑小单元"一个道理）。
- **合 sub-agent 的 worktree 后，汇总方（你）负责对账那批 task 状态** —— worktree 里的 sub-agent 不会可靠地碰共享 task 列表，这个缺口只能由合并方补。
- **`completed` = 已验证可用，不是"代码写了"**。需要人工/真机才能 done 的（真机验签、E2E QA、设计定稿），task 保持 open 或加注，并把缺口记进 tech-debt —— 别在骨架阶段就关。
- **session 末或合一批活后**，更新 `docs/progress.md` 顶部"最近对账"日期，顺手改 roadmap / tech-debt 对应条目，别攒到一次性审计。

## First action on every session that's about to change code

Before touching files, check where you are:

```
git branch --show-current
pwd                            # main worktree or .claude/worktrees/<x>?
```

Three cases:

1. **You're in a `claude/<auto>` branch in a worktree** → user just opened a fresh session via the UI. Read their first concrete instruction, derive a branch name (`feat/<name>` / `fix/<name>` / `chore/<name>`), and run `git branch -m <new-name>` before the first commit. If the instruction is too vague to name yet (e.g. "看看 X 是怎么实现的"), leave the rename until scope is clear or until the first edit.

2. **You're already on a `feat/*` / `fix/*` / `chore/*` branch in a worktree** → continue on it unless the user clearly switches topic. If they switch topic, suggest finishing/parking the current branch first rather than mixing scopes.

3. **You're in the main worktree on `main`** → for any code change, do NOT commit to `main`. Either:
   - **(preferred)** look up existing branches with `git branch -a | grep -E '(feat|fix|chore)/'` and `git for-each-ref --sort=-committerdate refs/heads/`, scan for one matching the topic; if a match exists, tell the user the path and ask them to open a session there.
   - **(fallback)** create a new worktree+branch with `git worktree add .claude/worktrees/<tail> -b <prefix>/<tail> main`, then tell the user "open a new session in `.claude/worktrees/<tail>` to continue" — current session can't move into it.
   - The main-worktree session itself stays in read-only / planning / status-check mode.

Inferring `feat/` vs `fix/` vs `chore/` from the user's phrasing:
- "加 / 实现 / 新功能 / add / implement / new" → `feat/`
- "修 / fix / bug / 不对 / 报错" → `fix/`
- "重构 / 清理 / 改名 / refactor / cleanup / rename / 整理" → `chore/`
- Ambiguous → ask once, in one short question.

## When user says...

- "开个 feat/foo" / "start a feature" → if not already in a worktree, create worktree + branch off `main`, tell the user the path to open a new session in
- "改 X 功能 / 修 Y bug" without naming a branch → run the "First action" decision tree above
- "把分支合回 main" / "merge this back" → fetch, judge size, run the right merge variant, typecheck, clean up worktree+branch, remind about `git push origin main`
- "清一下 stale worktree" / "clean stale worktrees" → list with `git worktree list`, check each with `git rev-list --count main..<branch>`. Zero-commit ones can be force-removed; non-zero ones get listed for the user to decide.
- "把当前分支改名" → `git branch -m <new-name>` from inside the worktree
